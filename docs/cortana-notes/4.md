# Detailed Migration Plan: talos-mixed → talos-home-ops

## 1. Backup Inventory — What You Have Now

### talos-mixed (existing cluster) runs these backup systems:

| System | What it backs up | Where it stores | Format |
|---|---|---|---|
| **Volsync (Restic)** | PVCs for ~60+ apps across all 3 clusters | NFS on Voyager: `/mnt/daena/kubernetes/volsync` | Restic repo |
| **Barman (CNPG)** | PostgreSQL databases (authentik, sonarr, radarr, paperless, dispatch, litellm, etc.) | S3 on LAN: `s3://postgresql/<app>/` | Barman base backups + WAL archive |
| **kopiur (Kopia)** | PVCs for ~60+ apps across all 3 clusters | NFS on Voyager: `/mnt/daena/kubernetes/volsync` | Kopia repo |

**Key point:** Both volsync AND kopiur are deployed in the existing cluster. They write to the same NFS path. The new cluster will use kopiur exclusively.

### What Barman protects (survives rebuild automatically):

Every CNPG-backed Postgres app has:
- Daily base backups at `s3://postgresql/<app>/<app>/`
- Continuous WAL archiving to the same prefix
- `bootstrap.recovery` configured in the component — **a rebuilt cluster with the same `serverName` will automatically restore from the latest Barman backup**

This is the **most important backup for the rebuild**. The Barman data lives on your LAN S3 (s3.davidstewen.com), completely outside the cluster. It survives node wipes, cluster rebuilds, everything.

## 2. What You Will Lose

| Data | Survives? | How to recover |
|---|---|---|
| **PostgreSQL databases** (CNPG apps) | ✅ Yes | Barman backups on S3 — automatic recovery on rebuild |
| **Volsync/Kopia PVC backups** | ✅ Yes (on NFS) | Still on Voyager at `/mnt/daena/kubernetes/volsync` — can restore manually or let kopiur build up |
| **Talos machine configs** | ✅ Yes | In Git (`talos-home-ops/talos/topf/`) |
| **Flux/GitOps state** | ✅ Yes | In Git (`talos-home-ops/kubernetes/`) |
| **1Password secrets** | ✅ Yes | In 1Password (never in Git) |
| **Cluster-internal state** | ❌ Lost | etcd data, pod logs, running configs — rebuilt from Git |
| **Volsync ReplicationSource/Destination CRs** | ❌ Lost | Replaced by kopiur CRs |
| **Barman backup history** | ✅ Yes (on S3) | But the new cluster's CNPG will point to the same S3 path and recover |

**Bottom line: No real data loss.** The two critical backup targets (Barman on S3 for Postgres, NFS for PVC snapshots) both survive the rebuild.

## 4. Backup Transition Strategy

### volsync → kopiur transition

```
Timeline:
├── Before rebuild:  volsync + kopiur both running (dual backup)
├── After rebuild:   volsync CRs gone, kopiur takes over
├── Transition period: kopiur builds snapshots (first snapshot takes time)
└── After 1-2 weeks: volsync backup history is stale, kopiur is primary
```

**During transition:**
- kopiur will start fresh snapshots immediately
- Old volsync data sits on NFS untouched — can be used for manual restores if needed
- No conflict: volsync and kopiur write to the same NFS path but use different repo structures

**If you need to restore from volsync during transition:**
```bash
# List volsync snapshots
just volsync list ns=<namespace> app=<app>

# Restore from volsync
just volsync restore ns=<namespace> app=<app>
```

### Barman recovery (automatic)

When CNPG clusters are created on the rebuilt main cluster:

1. CNPG sees `bootstrap.recovery` with `barmanObjectStore`
2. It connects to `s3://postgresql/<app>/<app>/` on s3.davidstewen.com
3. Finds the latest base backup
4. Restores the database
5. Replays WAL up to the point of failure

**This is fully automatic.** You don't need to do anything. The `cnpg.io/skipEmptyWalArchiveCheck: enabled` annotation handles the fact that the destination archive is non-empty (from the old cluster).
